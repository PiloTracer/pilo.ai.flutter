# Data layer standard — template

> **Template.** Copied to `{FLUTTER_STANDARDS_ROOT}/YYYYMMDD-DATA_LAYER_STANDARD.md` with tokens filled from `STACK.md` and foundation doc 04.

**Owned by:** `@flutter-data` · **Enforced by:** `@flutter-verify` D7, concept FLS-09.

---

## 1. Models: three shapes, not one

| Shape | Lives in | Purpose | Shaped by |
|-------|----------|---------|-----------|
| **DTO** | `data/dtos/` | Exactly the wire format | The API |
| **Entity** | `domain/entities/` | The business concept | The domain |
| **View state** | `presentation/` | What a screen renders | The screen |

Reusing a DTO as the domain model couples the app's core to someone else's JSON. When the API adds a field, renames one, or nests an object, the change propagates into widgets. **Mapping is the point**, and the mapper is where wire-level weirdness is quarantined.

Exception: `REPLACE:MODEL_COLLAPSE` may be set to `collapsed` for a small app with a fully-owned API. This is a recorded decision with a stated migration cost, not a default.

## 2. Serialisation

- Generated by `REPLACE:SERIALIZATION`, never hand-written. Hand-written `fromJson` is where the null crashes live.
- Generated files are **committed**, and regenerated whenever the source changes. Stale generated output is a verification failure.
- **Nullability mirrors the wire contract, not optimism.** If the API can omit it, the DTO field is nullable — and the mapper decides what absence means for the domain.
- **Unknown enum values must not crash.** Every wire enum has an `unknown` fallback. A new server-side status value should not brick the app for everyone who hasn't updated.
- **Numbers:** money and precise quantities are `Decimal` or minor-unit integers end-to-end, never `double`. Document the scale and rounding.
- **Dates:** parsed to UTC at the boundary, stored as UTC, formatted at display time only.
- **Defensive parsing at the boundary:** a malformed payload produces a typed failure, never an uncaught exception in a widget.

---

## 3. Repositories

- **Interface in `domain/`, implementation in `data/`.** The interface names the business capability; it never mentions HTTP, SQL, or cache.
- Returns domain entities and typed failures. No DTOs, no `Response`, no `Exception` from a client library.
- **Error mapping is total.** Every exception the sources can throw maps to a failure — including the ones you did not anticipate, via a catch-all that wraps and reports.
- One repository per aggregate or bounded capability, not one per screen and not one per endpoint.
- Repositories are **stateless apart from their cache**, and the cache is explicit.
- No business rules in a repository — it fetches, persists and maps. Rules belong in the domain.

## 4. Sources

| Source | Responsibility |
|--------|----------------|
| Remote | One API surface. Endpoint paths, serialisation, HTTP semantics. Throws typed transport exceptions |
| Local | One store. Queries, writes, migrations. Throws typed storage exceptions |
| Secure | Secrets only, through the platform keystore/keychain |
| Platform | Device capabilities via `@flutter-platform` channels |

Sources never talk to each other. The repository orchestrates them — that is its job.

**HTTP client configuration** (`REPLACE:HTTP_CLIENT`): base URL per flavor, timeouts (`REPLACE:CONNECT_TIMEOUT_MS` connect, `REPLACE:RECEIVE_TIMEOUT_MS` receive), auth interceptor with a **single-flight** token refresh, retry with exponential backoff and jitter for idempotent requests only, and logging that redacts credentials and PII.

## 5. Local store selection

| Need | Choice |
|------|--------|
| A handful of scalar preferences | `shared_preferences` |
| Credentials, tokens, keys | `flutter_secure_storage` — **only** this |
| Relational data, queries, joins, reactive streams, typed migrations | `drift` |
| Documents, simple object graphs, high write volume | a document/NoSQL store per `STACK.md` |
| Files, images, exports | filesystem via `path_provider`, with an explicit cleanup policy |

`shared_preferences` is plaintext on disk. Anything sensitive goes to secure storage; anything structured goes to a real database. Storing JSON blobs in preferences to avoid a schema is a decision to have no schema.

## 6. Migrations

Non-negotiable, because the failure mode is user data loss.

1. **Numbered and ordered.** `001_`, `002_` — never reordered, never renumbered.
2. **Idempotent.** Running twice must be safe. Verified by actually running it twice.
3. **Forward-only** in shipped versions. There is no downgrade path on a user's device.
4. **Tested from every shipped schema version**, not just the previous one. Users skip versions.
5. **Destructive steps require explicit human approval** in the request. An agent never drops or truncates.
6. **Data-preserving by default.** Widening, defaulting and backfilling before removing.
7. **Failure is handled**: a failed migration must leave a recoverable state and a reportable error, not an app that crashes on launch forever.

Every migration ships with a test that seeds the old schema, migrates, and asserts the data survived.

## 7. Caching

Every cached entity declares a policy — undeclared caching is the source of "why is it showing old data".

| Field | Values |
|-------|--------|
| Strategy | network-only · cache-first · cache-then-network · network-then-cache |
| TTL | duration, or "until invalidated" |
| Invalidation | what event clears it |
| Staleness display | does the UI indicate stale data? |
| Eviction | size or count bound, and what is evicted first |
| Scope | per-user? cleared on logout? |

**Cache clearing on logout is mandatory** for anything user-scoped. Leaving the previous user's data on disk is a privacy incident.

## 8. Offline

If the app claims offline support (SPEC §10), each of these has an answer before implementation:

- Which operations work offline, and which fail with what message.
- Where queued mutations live, and whether they survive process death.
- The retry and ordering policy for the queue.
- **The conflict policy**: last-write-wins, server-wins, merge, or user-resolves. "We'll figure it out" means last-write-wins with silent data loss.
- What the user sees while offline, while syncing, and after a sync conflict.
- The bound on queue growth.

## 9. Data classification

Every persisted field is classified. The classification determines the store.

| Class | Examples | Store | Logging | On logout |
|-------|----------|-------|---------|-----------|
| Secret | Tokens, keys, passwords | Secure storage only | Never | Deleted |
| Sensitive personal | Name, email, location, health, financial | Encrypted store | Never | Deleted or re-keyed |
| Personal | Preferences, non-identifying settings | Standard store | Redacted | Retained if not user-scoped |
| Public | Reference data, catalogues | Any | Free | Retained |

Record the full inventory in foundation doc 04 §4. `@flutter-security storage` audits code against it.

## 10. Testing

| Target | Test |
|--------|------|
| Mapper | Golden JSON fixture → entity; include missing fields, nulls, unknown enums, malformed input |
| Repository | Fake sources; assert every error maps to the right failure |
| Local source | Real in-memory database instance, not a mock — mocks do not have schemas |
| Migration | Seed old schema → migrate → assert data; run twice for idempotence |
| Cache | Assert the declared policy: hit, miss, expiry, invalidation |
| Offline | Simulate offline; assert queue, retry and conflict behaviour |

Fixtures are **real captured payloads**, sanitised. Hand-written fixtures test the fixture author's beliefs about the API, not the API.
