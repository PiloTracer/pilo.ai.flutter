# Plan — Make Flutter Agent OS produce world-class UI/UX

## 1. What you asked for, restated

Make the framework produce Flutter apps whose **visible quality** matches their engineering quality — software a non-technical client calls "awesome" instead of "a bit basic". The transcript in `TMP/ui-reference-transcript.md` is a **reference for the problem**, not a spec: its demo is a Python desktop app, its "last 30 centimetres" means *the final polish layer the client sees*, and its three rules are the 80% of the "cheap app" signal. Your ask: analyze it, research additional authoritative resources, and upgrade the framework so generated apps are professional, clear to anyone, and sellable. Plan first — nothing is implemented until you approve.

## 2. What the transcript actually claims (distilled)

Two apps, identical logic; one sells at 10× the other. The difference is never in the data layer — it is in what the eye judges in under a second. Three mechanical signals read as "free app":

1. **Random spacing.** Seven ad-hoc padding values on one screen read as disorder. The fix is a fixed scale (4/8/16/24/32 — multiples of 4, so every combination lands on one grid), few values per screen, and values stored as constants so a `padding: 13` stands out in a diff. *Rule, not taste.*
2. **No hierarchy.** When title, number, labels and buttons are all ~16px (ratio 1), the eye has no entry point and the client reads the effort as "badly made". The fix: pick **one dominant element per screen** at ~2.5× the body size (author's heuristic, honest range 2–3×). The rule's real value: it *forces the decision* of what matters on each screen.
3. **Factory colors.** The default library blue/green/red screams "nobody made a color decision", and six saturated colors fighting on a one-task screen is the loudest cheap signal. The fix: **one accent + a neutral gray ramp**, and the accent appears in **exactly one place per screen — the primary action**.

The remaining 20%: loading states, error messages that don't scare, narrow screens, keyboard focus, sunlight contrast — plus the Stanford credibility study (design "look" was 46.1% of all credibility comments, Fogg et al. 2002 — verified against the original report). Key framing for us: **none of this is artistic talent; it is lintable rules** — which is exactly what this framework is built to enforce.

## 3. Gap analysis — what the framework already has vs. what is missing

Evidence from the current tree (both suites green: `framework-verify` 302 checks / `self-test` 35 assertions):

**Already covered (do not rebuild):**
- Token discipline: `THEMING_STANDARD` — theme as single source, spacing scale token, TextTheme, motion tokens, dark mode; `FLUTTER_CONVENTIONS` bans magic numbers in widgets.
- Six UI states: `FEATURE_SPEC_STANDARD` §6; `flutter-verify` D3.
- Contrast, tap targets, text scale, focus: `ACCESSIBILITY_STANDARD` + FLS-10 + `flutter-a11y`.
- Hardcoded `Color(0x…)` literals: `dart-hygiene-check.sh` (BLOCKER).
- Performance, security, layer boundaries, test integrity: existing skills/concepts.

**Missing (the actual gap):**
1. **No spacing-rhythm enforcement.** THEMING promises a "grep check on raw EdgeInsets numbers" (§10) but `dart-hygiene-check.sh` only checks `Color(0x…)` — `EdgeInsets.all(13)`, `SizedBox(height: 7)`, `Colors.blue` and `fontSize: 14` literals all pass today.
2. **No hierarchy rule anywhere.** No standard, SPEC section, or concept asks "what is the one dominant element on this screen?" — the transcript's rule 2 and the decision it forces.
3. **No accent discipline / factory-color rule.** THEMING defines semantic colors but never "one accent per screen, primary action only, no default palette".
4. **No visual-craft review lens.** FLS-01…12 cover correctness, not perceived quality. `flutter-verify` has 14 dimensions — none judges craft.
5. **No UX-clarity guidance for non-technical users** (plain-language errors, Jakob/Hick/Fitts, skeleton-vs-spinner thresholds) — the transcript's 20%, currently unowned.
6. **Scaffold generates a theme but not the craft wiring** (no spacing `ThemeExtension` with the scale, no neutral-ramp/accent split).

**Cohabitation note:** `.ai.ui` owns design *tokens* when installed (COHABITATION.md). The new rules govern **how Flutter consumes tokens** and provide defaults when no sibling exists — same deferral pattern THEMING already uses. No contract change.
